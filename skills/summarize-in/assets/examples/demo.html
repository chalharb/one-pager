How edge networks work

An edge network keeps copies of your content, and increasingly your code, in data centers close to users. Most requests are answered a few milliseconds away instead of crossing an ocean to your origin server.

The problem is distance

Light in optical fiber covers about 200,000 km per second. A user in Sydney talking to a server in Virginia, roughly 15,700 km away, waits at least 160 ms per round trip, however fast either end is.

Round trips stack up. A fresh HTTPS request needs one for the TCP handshake, one for TLS 1.3, and one for the request itself: about half a second before the first byte. Put a server 10 ms from the user and the same three trips take 30 ms.

How a request finds the edge

Anycast announces one IP address from every location over BGP, so ordinary internet routing delivers each user to a nearby point of presence (PoP). DNS steering does the same job by answering each resolver with the address of a PoP near it.

The PoP finishes the TCP and TLS handshakes, then serves from cache. On a miss it asks an origin shield, a mid-tier cache, so a thousand PoPs missing at once become one request to your origin.

Key terms

PoP
A data center full of edge servers
Origin
Your server, the source of truth
Hit ratio
Share of requests served from cache
TTL
How long a cached copy counts as fresh
Purge
Evicting cached copies before their TTL ends

Most web latency is round trips, not bandwidth. The edge wins by making every round trip short, starting with the handshakes.

What runs at the edge

  • Caching of assets, pages, and API responses.
  • TLS termination close to the user.
  • Security: DDoS absorption, WAF rules, bot checks.
  • Transforms: image resizing, compression, redirects.
  • Edge functions: your code, run in lightweight isolates at every PoP.

Telling the edge what to keep

The origin controls caching with the Cache-Control response header. Browsers and shared caches such as CDNs read different directives, so one header can set both.

  • max-age=60 lets browsers reuse it for a minute.
  • s-maxage=86400 lets the edge keep it for a day.
  • stale-while-revalidate serves the old copy while a fresh one is fetched in the background.

The cache key, usually host plus URL, decides what counts as the same object. Varying it on cookies or many headers splits one object into thousands and sinks the hit ratio.

Code at the edge

Edge functions use the Fetch API shape most edge runtimes share: take a Request, return a Response. This one passes API calls through and caches everything else for an hour.

Trade-offs

  • Staleness. A cached copy is wrong from the moment the origin changes until its TTL ends or you purge it.
  • Data gravity. Code moves to the edge easily; databases do not.
  • Tight limits. Edge functions get small CPU-time and memory budgets.
  • Harder debugging. One request can behave differently in each of hundreds of locations.

Watch for

An edge function that queries a database in one region can be slower than no edge at all, because every query pays the long round trip.
