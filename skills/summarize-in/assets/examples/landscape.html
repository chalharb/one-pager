The TLS 1.3 handshake

Before any HTTPS data moves, client and server agree on keys and the server proves its identity. TLS 1.3 does this in one round trip, half of what TLS 1.2 needed, and encrypts everything after the first two messages.

Step by step

  1. ClientHello. Supported versions and ciphers, the server name (SNI), and a guessed key share, usually X25519.
  2. ServerHello. The chosen cipher and the server's key share. Both sides now compute the same secret with ECDHE.
  3. Server proof. Encrypted certificate chain, a signature over the handshake so far, and a Finished MAC.
  4. Client Finished. The client checks the chain and signature, sends its own Finished, and can send the request in the same flight.

Wrong guess

If the server doesn't support the guessed key group, it replies with HelloRetryRequest and the handshake costs a second round trip.

0-RTT resumption

A returning client can send a pre-shared key from an earlier session and put request data in its very first flight. The catch: that early data can be replayed by an attacker, so servers should accept it only for idempotent requests such as GET.
